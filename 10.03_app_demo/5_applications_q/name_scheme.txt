
Naming of the example applications (QBUS / QBone)
=================================================

Same scheme as the UNIBUS examples in "5_applications_u", one directory per
example, one script per way of running it. What is QBUS-only is marked "QBUS"
below.

QBUS	These examples drive a real QBUS backplane. There is no emulated CPU:
	the cpu20 and cpu34 directories of the UNIBUS set have no counterpart
	here, and neither has m9312 - the M9312 is a UNIBUS boot ROM - nor
	unixv1, whose RF11/RS11 disk is a UNIBUS device.


Directories
-----------
<OS>.<boot medium>		rt11.rl02, unixv6.rl02, rsx11.mscp, rt11.rx01

The medium is the drive the example boots from, not the controller: rl02, rk05,
rx01, rx02, mscp. Directories without a medium hold something else: "memory" the
memory emulation.

QBUS	Three examples run a MicroVAX II (KA630) instead of a PDP-11 and say so
	with "_uvax" in front of the medium: 43bsd_uvax.mscp, vms44_uvax.rl02,
	vms73_uvax.mscp. A MicroVAX boots from its own console ROM, so those
	scripts deposit no bootloader - they only emulate the drives.

An example directory holds only what belongs to that setup alone: its scripts, a
program it is the only user of (zkma.ptap), a SimH configuration for comparison
(*.simh_pdp11, boot.ini), a note on the system it boots (NanoVMS044-1M.txt).
What several examples share sits in a directory of its own beside them:

	diskimages	every disk and floppy image
	bootloaders	the bootloader listings a script deposits


Scripts
-------
<OS><version>[_<pdp11-model>].<boot device><unit>.sh

	rt11v5.5.dlx.sh
	xxdp22-25.dlx.sh

A script is no longer a shell wrapper around a .cmd file - there is no .cmd file
any more. The script IS the demo command file and starts with

	#!/root/10.03_app_demo/4_deploy/demo --verbose

so it runs as "sudo ./rt11v5.5.dlx.sh", with further options if wanted. demo
ignores the "#!" line as it ignores any line starting with "#". A file the
script names is looked up next to the script, so no "cd" and no absolute paths
are needed: "../bootloaders/dl.lst", "../diskimages/<image>", or a plain name
for the one file that belongs to this example alone. Files the run creates land
in the directory it was started from.

<OS><version>	rt11v5.5, rsx11m4.8, unixv6, xxdp22-25, 211BSD, vms73.
		A script that serves two versions names both: xxdp22-25.
<pdp11-model>	The PDP-11 the setup is for, when it matters: _23, _73, _34.
		Two models where the setup serves both: _23_73. Omitted when
		the setup is model independent, and on the MicroVAX examples.
<boot device>	The DEC bootstrap mnemonic of the drive booted from, which is
		also the name of the bootloader listing the script deposits
		from "bootloaders":
			dl	RLV12 / RL01, RL02	dl.lst
			dk	RKV11 / RK05		dk.lst
			du	MSCP (RQDX3, RA.., RD..)  du.lst
			dx	RXV11 / RX01		dx.lst
			dy	RXV21 / RX02		dy.lst
		QBUS: the controllers are the QBUS members of those families;
		demo names the device the same on both buses (rl, rk, uda, rx,
		ry), so a script differs from its UNIBUS twin only in what the
		hardware is.
<unit>		The drive number booted from: dl0, dl1, du0, ...
		"x" when the script mounts several units and leaves the choice
		to the operator: a script for a real PDP-11 cannot start the
		CPU, it only installs the bootloader and prints the start
		addresses (10000 for unit 0, 10010 for unit 1, ...). So
		rt11v5.5.dlx.sh serves DL0 and DL1 and is one file, where there
		used to be an identical rt11v5.5fb_dl0.sh and rt11v5.5sj_dl1.sh.

Suffix "_shared" instead of a unit: the drive is not an image file but a shared
host directory, exposed as a DEC filesystem (rt11v5.5_dl_shared.sh).

Most scripts still carry the older form, <OS>_<boot device><unit>_<pdp11-model>
(unixv6_dl0_23.sh, 211BSD_du0_73.sh, rt11v3_rx0.sh); they get the name above
when they are next revised.

A script whose disk image is not available is renamed to ".sh.MISSING-IMAGE"
and made non-executable, so it cannot be started by accident and says why in its
name. Two exist: rsx11.mscp/rsx11m4.8_du0+rl_23_73.sh.MISSING-IMAGE (rsxm70 on
DU1) and rsx11mp4.8_du0+rl_23_73.sh.MISSING-IMAGE (rsx11mp_4_8_bl70 on DU0 and
rsxm70 on DU1). Rename them back when the images turn up.


Images
------
All disk and floppy images live in ONE directory, "diskimages", and every script
reaches them by the same relative path:

	p image ../diskimages/rt11v5.5.rl02.dsk
	p img   ../diskimages/rt11v03-1.rx01.dsk	(RX drives use "p img")

They used to sit next to the script that mounts them, under whatever extension
they arrived with - .dsk, .rl02, .img, .RX2, .r54, .RL2 or none at all. One
directory and one scheme mean one name per disk, and a new example costs no
image it can share.

	<OS><version>[_<content>][_<pdp11-model>].<medium>.dsk[.gz]

	rt11v5.5.rl02.dsk.gz		system disk
	rt11v5.5_games.rl02.dsk.gz	second volume, named by content
	rt11v5.5_34.ra80.dsk.gz		the RT-11 system disk built for an 11/34
	rt11v03-1.rx01.dsk.gz		RT-11 v3 distribution floppy 1
	vms073.rd54.dsk.gz		QBUS: VMS 7.3 for the MicroVAX

<medium>	The drive the image is mounted in, NOT the file format - the
		format is a plain block image in every case:
			rl02  rk05  rx01  rx02		and the MSCP drives
			ra70  ra80  ra82  rd53  rd54
		Where a script sets "p type", that is where the medium comes
		from. An MSCP volume keeps the type it is mounted as even when
		"p uis 1" takes the block count from the file, so a .ra80 image
		may well be larger than a real RA80.
		QBUS: rd53/rd54 are the MicroVAX-era MSCP disks of the RQDX3
		and appear only here; the UNIBUS set has ra92 instead.
.dsk		Always last, so every image has one known extension whatever
		the medium is. This is what lets .gitignore hold a single
		pattern, and it keeps names like "RTRKV4.00" - where the ".00"
		is a version, not a medium - from being mistaken for one.
		RTRKV4.00.rk05.dsk.gz says both.
.gz		The compressed master, and the only form kept in the
		repository. See "Compression" below.

56 images, all of them different: unlike the UNIBUS set, which held the same
disk two or three times over, this collection had one copy of each already -
what it lacked was one place and one naming.

Volumes a script mounts but does not ship are scratch disks, and demo creates
them empty on first use, in "diskimages" like every other image:
scratch1.rl02.dsk, scratch2.rl02.dsk, scratch3.rl02.dsk, scratch01.rl02.dsk,
scratch1.rk05.dsk, scratch1.ra80.dsk, scratch.rd53.dsk, test_du1.ra70.dsk.

"diskimages" also holds the sources the images came from:

	rx01_disk_images_woodstock.url
	rx02_disk_images_ak6dn.url
	unixv6_images_shoppa.url
	woodstock_rx01_floppies.pdf


Compression
-----------
Only the ".gz" is kept in the repository; the expanded image is a product of a
run and .gitignore drops every "*.dsk". When demo cannot open the image a script
names, it looks for "<image>.gz" next to the script and expands it with zcat
into the directory it found it in - so "diskimages", beside its own ".gz"
(10.02_devices/2_src/storageimage.cpp). It stays there, and every later run,
from wherever it is started, opens it directly.

Every image has its ".gz", with one exception: JH_DU1.ra70.dsk.gz, the uda1 data
disk of the RSX11M-PLUS example, is 296 MB and over the 100 MB limit GitHub
enforces on a single file. It is excluded by name in .gitignore, and
diskimages/JH_DU1.ra70.dsk.gz.txt records what it is and its checksums. Nothing
breaks without it: uda1 comes up as an empty RA70, the system on uda0 boots.


Bootloaders
-----------
"bootloaders" holds one copy of each MACRO-11 listing a script deposits into
memory, and every script reaches it the same way:

	m ll ../bootloaders/dl.lst

Five files, where the examples used to carry eleven copies between them - dl.lst
alone existed four times, in two versions that differed only in line endings.
The name is the boot device code of the drive the listing boots from, so a
script and its bootloader spell the same thing:

	dl.lst		RLV12 / RL01, RL02	dy.lst	RXV21 / RX02
	dk.lst		RKV11 / RK05
	du.lst		MSCP (RQDX3, RA.., RD..)
	dx.lst		RXV11 / RX01

Each is a modified copy of the DEC M9312 boot PROM for its controller, with one
entry address per unit: 10000 boots unit 0, 10010 unit 1, and so on. A "d"
script cannot start a real PDP-11, so it deposits the listing, prints those
addresses and leaves the rest to the operator.

QBUS	These five listings are byte for byte the ones in
	5_applications_u/bootloaders: a bootloader talks to controller
	registers in the I/O page, which are the same on both buses. Missing
	here, because the devices are UNIBUS only: the four 23-*.lst M9312 PROM
	listings and rf11.lst.

Not here, because it is not a bootloader: memory/zkma.ptap, the MAINDEC memory
diagnostic, loaded with "lp".
